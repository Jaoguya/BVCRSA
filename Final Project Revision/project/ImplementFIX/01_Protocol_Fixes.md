# F1 — Bind `S_Q` to the authorized query

**Reviewer:** R3-1 · **Severity: blocking** · **The most serious finding in the review set.**

## The defect

Phase 4 has the user send `\mathcal{S}_Q` (selected bitmap positions) and the
cloud homomorphically aggregates the corresponding entries. Nothing anywhere
in the protocol binds `\mathcal{S}_Q` to `B_Q` — the bitmap actually produced
by the authorized trapdoor `T_Q`.

A user authorized for *any* range can therefore submit *any* position set and
receive a valid, verifiable aggregate over records they were never entitled
to. Theorem 6 proves the aggregate is correct *with respect to the presented
`\mathcal{S}_Q`*, which is precisely the wrong statement.

## Options

| | Approach | Cost | Cloud learns `B_Q`? |
|---|---|---|---|
| (a) | Cloud recomputes `B_Q` and rejects `\mathcal{S}_Q \not\subseteq B_Q` | 1 bitmap AND | yes |
| (b) | User proves membership against authenticated blocks | extra round + proof | no |
| (c) | TDA-side authorization check | folds into F3 | no |

**Recommended: (a) + (c).**

(a) is a handful of lines and is easy to prove. The cloud already observes
matched canonical nodes and selected positions — both are in the declared
leakage profile `\mathcal{L}_{\mathrm{BVCRSA}}` — so it learns nothing new.
(b) preserves marginally more privacy at the cost of a round trip and a new
proof system, which is hard to justify for leakage already conceded.

## Fix — insert into Phase 4, before aggregation

```latex
\paragraph*{Step 4: Selection Authorization}

Before performing any homomorphic aggregation, the cloud verifies that the
requested position set was derived from the authorized query. Having evaluated
$T_Q$ in Step~1, the cloud holds the matched canonical node set
$\mathcal U_Q$ and the corresponding protected bitmap blocks. It therefore
recomputes the conjunctive query bitmap
\begin{equation}
\widehat B_Q
=
\bigwedge_{j=1}^{d}
\ \bigvee_{u\in\mathcal U_Q\cap\mathcal C_j}
\widetilde B_{u}\oplus
\mathsf{PRG}\!\left(F(K_u,\cdot),\,N_{e_q}\right),
\label{eq:p4-cloud-bitmap}
\end{equation}
and accepts the aggregation request only if
\begin{equation}
\mathcal S_Q\subseteq\mathsf{Supp}(\widehat B_Q)
\quad\wedge\quad
|\mathcal S_Q|\le N_{e_q},
\label{eq:p4-selection-check}
\end{equation}
aborting otherwise. Consequently, a user cannot obtain an aggregate over any
position outside the bitmap generated by its own policy-authorized trapdoor.
```

⚠️ **Key-availability problem.** Eq. `p4-cloud-bitmap` needs `K_u` to unmask,
and the cloud does not have it — by design, that is what stops the cloud
reading bitmaps. Two ways out:

- **(a1)** The cloud performs the check on *masked* blocks. Positions are
  mask-invariant under a fixed `(b, ν_{u,b})`, so the cloud can verify that
  each `pos ∈ \mathcal{S}_Q` falls inside a block belonging to a matched node,
  but not that the bit is set. **Weaker — catches cross-node theft, not
  within-node.**
- **(a2)** The user forwards the recovered `K_u` for matched nodes only, with
  the request. The cloud can then unmask exactly those nodes it already
  matched. **Full check, at the cost of revealing matched-node bitmap contents
  to the cloud** — which must be added to `\mathcal{L}_{\mathrm{BVCRSA}}`.

**Recommend (a2) plus F3.** It gives a real check, and the added leakage is
matched-node bitmap contents — the cloud already learns node identity, result
cardinality, and access pattern. Update the leakage profile accordingly and
say so in the threat model rather than hoping nobody notices.

# F2 — Bind node policies to record policies

**Reviewer:** R3-2 · **Severity: blocking**

## The defect

A user satisfying `\mathcal P_u` recovers `K_u`, reconstructs node `u`'s
bitmap, and can aggregate every record at those positions — including records
whose own `\mathcal P_i` they do not satisfy. Node-level authorization
silently confers record-level access.

## Fix — containment invariant, stated and enforced

```latex
\paragraph*{Policy Containment Invariant}

To prevent node-level authorization from implying unauthorized record access,
the Edge Gateway enforces, for every record $i$ and every canonical node
$u\in\mathsf{Path}(u_{i,j})$,
\begin{equation}
\mathcal P_u\Rightarrow\mathcal P_i,
\label{eq:policy-containment}
\end{equation}
that is, any attribute set satisfying the node policy also satisfies the
record policy. Records whose policy is not implied by the policy of a
containing canonical node are assigned to a separate index partition. Under
Eq.~\eqref{eq:policy-containment}, a user able to reconstruct $B_u$ is by
construction authorized for every record whose position it contains.
```

Then add to Phase 2 Step 2's acceptance predicate:

```latex
\land\;\mathcal P_{u}\Rightarrow\mathcal P_i
\ \ \forall u\in\mathsf{Path}(u_{i,j})
```

**Alternative** if the containment constraint is too restrictive for the
deployment: filter per record at aggregation time, including only entries
whose `\mathcal P_i` the requester satisfies. Costs one ABSE check per
selected record — measurable, and it belongs in Experiment 5's verifiable arm.

⚠️ Pick one. Containment is cheaper but constrains how policies may be
assigned; per-record filtering is general but adds `O(r)` pairing operations
to every query, which will show up in Exp 2 and Exp 5.

# F3 — TDAs verify query authorization

**Reviewer:** R3-3 · **Severity: blocking** · Completes F1.

## The defect

TDAs verify, via Chaum–Pedersen DLEQ, that their own partial decryption is
well-formed. They never verify that the ciphertext originated from an
authorized query. They are an unconditional decryption oracle for any
well-formed EC-ElGamal ciphertext.

## Fix — authorization token checked before partial release

```latex
\paragraph*{Step 3: Authorized Partial Decryption}

The user submits to each TDA the aggregation request
\begin{equation}
\mathcal R_Q
=
\bigl(
e_q,\;qid,\;Root_{e_q},\;
h_{\mathcal S}=H(\mathsf{enc}(\mathcal S_Q)),\;
CT_{\mathrm{sum}},CT_{\mathrm{count}},\;
\sigma_{\mathrm{CS}}
\bigr),
\label{eq:p5-agg-request}
\end{equation}
where $\sigma_{\mathrm{CS}}$ is the cloud's signature attesting that
Eq.~\eqref{eq:p4-selection-check} was verified for $(qid,h_{\mathcal S})$.
TDA $\ell$ releases its partial decryption $D_\ell$ only if
\begin{equation}
\begin{split}
&\mathsf{DS.Verify}_{pk_{\mathrm{CS}}}
\bigl(\sigma_{\mathrm{CS}},
H(e_q\|qid\|h_{\mathcal S}\|CT_{\mathrm{sum}}\|CT_{\mathrm{count}})\bigr)=1\\
&\quad\land\;
e_q\ \text{is the finalized epoch}
\ \land\ ts<t_{\mathrm{exp}},
\end{split}
\label{eq:p5-tda-check}
\end{equation}
and aborts otherwise. Thus at least $t$ authorities must independently accept
the query authorization before any aggregate plaintext can be recovered.
```

Requires the cloud to hold a signing keypair `(pk_CS, sk_CS)` — add to
Phase 1 Step 4 credential distribution and to `\mathsf{Pub}`.

⚠️ This shifts trust: the TDAs now rely on the cloud's attestation. Since the
cloud is **malicious** in the threat model, note that this check prevents an
*honest-but-greedy user* from bypassing authorization, not a cloud–user
collusion. For that, the TDAs would need to verify the ABSE token themselves.
State the boundary explicitly rather than overclaiming.

# F4 — Instantiate ABSE concretely

**Reviewer:** R1-C2, R3-4, R3-5 · **Severity: blocking**

## The defect

Eq. `abse-interface` defines ABSE as a 7-tuple of algorithm names with
correctness conditions and no instantiation. Every security theorem is
conditional on unproven properties of an unspecified primitive.

## Fix — describe what the code actually implements

The prototype uses an AND-gate policy over a bilinear group. Write that down
rather than inventing something stronger.

```latex
\subsubsection*{ABSE Instantiation}

We instantiate $\mathsf{ABSE}$ as the composition of a key-policy
attribute-based keyword search scheme with an attribute-based key
encapsulation mechanism, both over the same bilinear group
$(p,\mathbb G_1,\mathbb G_T,e,g)$ and sharing a single master secret.
Access policies are AND-gates over the attribute universe $\mathcal U$: a user
key $SK_{\mathcal A}$ satisfies $\mathcal P$ iff
$\mathcal P\subseteq\mathcal A$.

\textbf{Setup.} $\alpha,\beta\xleftarrow{\$}\mathbb Z_p$;
$PP=(g,g^{\beta},e(g,g)^{\alpha})$, $MSK=(\alpha,\beta)$.

\textbf{KeyGen.} For $\mathcal A\subseteq\mathcal U$ sample
$r\xleftarrow{\$}\mathbb Z_p$ and output
$SK_{\mathcal A}=\bigl(D=g^{(\alpha+r)/\beta},\
\{D_a=g^{r}\cdot H_g(a)^{r_a},\ D'_a=g^{r_a}\}_{a\in\mathcal A}\bigr)$.
The per-user randomness $r$ is what yields collusion resistance: keys issued
to distinct users cannot be combined, since their $r$ values differ.

\textbf{Index/Token/Test.} $I_w$ and $Tok_{w'}$ are the standard
pairing-based keyword-search components, with the context epoch $e_c$ and
query identifier $qid$ bound into the hash input so tokens are randomized and
non-transferable across queries and epochs. $\mathsf{Test}$ evaluates a
pairing equation that holds iff $w=w'$ and $\mathcal A\models\mathcal P$.

\textbf{Enc/Dec.} Payload-key encapsulation is the same construction applied
to a random $\mathbb G_T$ element, from which the encapsulated key is derived
via $\mathsf{KDF}$.

Security rests on the Decisional Bilinear Diffie--Hellman assumption in
$(\mathbb G_1,\mathbb G_T)$. Keyword privacy against the cloud holds in the
random-oracle model under DBDH; collusion resistance follows from the
independence of the per-user randomisation $r$.
```

Then state the implementation:

```latex
The prototype instantiates the pairing group with BLS12-381 via
\texttt{py\_arkworks\_bls12381} (128-bit security), with a pure-Python
BN128 fallback through \texttt{py\_ecc}. All reported measurements use the
BLS12-381 backend.
```

⚠️ **This last sentence corrects a factual error.** The paper currently says
*"implemented with `py_ecc` over the BN128 bilinear curve."* `_shared/TA.py`
prefers `abse_fast.py` (BLS12-381), and the verification experiment imported
the Rust library unconditionally — so it was installed when the numbers were
taken. Run **Experiment 10**; it prints the live backend. Fix the text to
match, or pin `py_ecc` and re-run everything.

⚠️ Whatever is written must be checked against `_shared/abse_fast.py` and
`_shared/abse_real.py` before submission. The paper must describe the code
that produced the numbers.

# F5 — Provision the gateway with sensor HMAC keys

**Reviewer:** R1-C1 · **Severity: blocking**

## The defect

Phase 2 Step 2 has the gateway compute
`\mathsf{HMAC.Verify}_{K_{\mathrm{HMAC}}^{(i)}}(\cdot)` using a key that
Phase 1 Step 4 distributes only to sensors. The step cannot execute.

## Fix — master-key derivation

Cleaner than shipping the full key set: gateway state stays constant in the
sensor count, and it matches the existing KDF pattern.

Patch Eq. `gateway-keys`:

```latex
K_{\mathrm{sel}}\xleftarrow{\$}\{0,1\}^{\lambda},
\quad
K_{\mathrm{HMAC}}^{\mathrm{mas}}\xleftarrow{\$}\{0,1\}^{\lambda},
\quad
(pk_{\mathrm{DO}},sk_{\mathrm{DO}})\leftarrow\mathsf{DS.KeyGen}(1^\lambda),
```

with per-sensor keys derived from it in Eq. `sensor-keys`:

```latex
K_{\mathrm{HMAC}}^{(i)}
=\mathsf{KDF}(K_{\mathrm{HMAC}}^{\mathrm{mas}},ID_i\parallel\mathtt{hmac})
```

Patch Eq. `credential-distribution`:

```latex
\text{Edge Gateway}:\ (K_{\mathrm{sel}},sk_{\mathrm{DO}},
K_{\mathrm{HMAC}}^{\mathrm{mas}})
```

and Eq. `secret-state`:

```latex
\mathsf{Sec}_{\mathrm{GW}}
=(K_{\mathrm{sel}},sk_{\mathrm{DO}},K_{\mathrm{HMAC}}^{\mathrm{mas}})
```

Note the separation that preserves confidentiality:

```latex
The gateway derives $K_{\mathrm{HMAC}}^{(i)}$ for packet authentication but
never obtains $K_{\mathrm{AES}}^{(i)}$, which is derived from the independent
master key $K_{\mathrm{master}}$ retained by the TA. It can therefore verify
sensor packets but cannot decrypt record contents.
```

⚠️ **Threat-model consequence — state it.** The gateway can now forge sensor
packets. This compounds F6 / R7-C1. Theorem 1 (Sensor-Packet Authenticity)
must be restated to hold against the *cloud and external adversaries*, not
against the gateway. See `02_Proof_Fixes.md`.

# F6 — Scope the completeness claim honestly

**Reviewer:** R7-C1, R7-C2, R3-9 · **Severity: blocking**

## The defect

VQSA proves *"the cloud returned what the gateway committed."* It cannot prove
*"what the gateway committed is what the sensors sent."* The threat model
already concedes this — "verification is therefore relative to the
gateway-committed state" — but the abstract, contributions, and Theorem 7
claim "authenticated completeness" unqualified.

## Fix — propagate the qualifier

**Abstract**, replace:

> …to provide authenticated query-state integrity, completeness, freshness,
> and rollback resistance…

with:

> …to provide authenticated query-state integrity, completeness **relative to
> the gateway-committed state**, freshness, and rollback resistance…

**Contribution 4**, same change to "authenticated completeness".

**Add to the threat model**, making the boundary unmissable:

```latex
\begin{remark}[Scope of Completeness]
All completeness guarantees are stated relative to the state committed by the
Edge Gateway. VQSA detects omission, modification, substitution, and replay by
the cloud, but cannot detect fabricated canonical-node memberships or
falsified bitmap contents produced by the gateway prior to anchoring. A
gateway that commits an incorrect index is outside the threat model.
Extending detection to gateway misbehaviour---for example by requiring
sensors to co-sign their canonical-node metadata so that fabricated
memberships fail signature verification---is left as future work.
\end{remark}
```

⚠️ The sensor-co-signing sketch is worth including even as future work: it
shows the limitation was understood rather than discovered by the reviewer.
If it is actually implemented, completeness strengthens to *relative to
sensor-signed metadata*, which is materially stronger and defensible.
