# Reviewer 7

**Verdict: MAJOR REVISION** — five comments, focused on the gateway trust
model and on end-to-end costs that were never measured.

## Summary of position

Comments 1 and 2 attack the same structural weakness from two sides: the edge
gateway is a single point of trust, and blockchain anchoring cannot detect a
gateway that commits false state in the first place. Comments 4 and 5 say the
evaluation measures only offline cryptographic latency and ignores every
real-deployment cost.

---

## R7-C1 — Gateway monopolizes `K_sel`

> The edge gateway monopolizes the global master secret K_sel for bitmap
> masking, which creates a severe single point of trust. A compromised or
> malicious gateway can forge invalid index and bitmap commitments before
> anchoring them on the blockchain.

**Type:** architectural. **Severity: blocking.** Also R3-9.

Correct. `K_sel` derives every node key `K_u = F(K_sel, D_j ‖ u)`, and every
bitmap mask derives from `K_u`. One secret at one entity controls the entire
index and bitmap layer.

⚠️ **This gets worse under R1-C1's fix.** Resolving the HMAC key-distribution
inconsistency requires giving the gateway sensor HMAC keys — after which it
can also forge *sensor packets*, not just index state. The two fixes must be
designed together.

### Fix — pick a lane and be explicit

- **(a) Accept and scope it.** The threat model already says "a malicious
  gateway that constructs or commits an incorrect index is outside the threat
  model." Make that limitation prominent — in the abstract and contributions,
  not only in §IV. Currently the paper claims "authenticated completeness"
  unqualified, which overstates what is proven.
- **(b) Reduce the trust.** Split `K_sel` across multiple gateways with
  threshold derivation of `K_u`, or have sensors contribute entropy to node
  keys so no single party can regenerate all masks.
- **(c) Detect it.** Require sensors to co-sign the canonical-node metadata
  they generate, so a gateway that fabricates memberships produces
  commitments that fail sensor-signature verification.

**(a) is honest and cheap; (c) is the strongest without a redesign.** (b) is a
genuine protocol redesign — which is what R3 demands anyway.

## R7-C2 — Guarantees hold only against the cloud, not the gateway

> The integrity and completeness guarantees of the proposed protocol are only
> conditioned on the honest edge gateway. The current mechanism can only
> detect tampering or omission of indexes and bitmaps conducted by the cloud
> server during query execution, yet it cannot identify fake canonical indexes
> or falsified bitmap raw data deliberately generated by the edge gateway
> before it anchors Merkle roots on the blockchain.

**Type:** architectural — the precise consequence of C1. **Severity: blocking.**

VQSA proves *"the cloud returned what the gateway committed."* It cannot prove
*"what the gateway committed is what the sensors sent."* Blockchain anchoring
authenticates the commitment, not its correctness.

### Fix

Rewrite the completeness claim to say exactly this. The paper already uses the
phrase "completeness relative to the gateway-committed state" in the threat
model — R1's opening paragraph credits that as an improvement. **Propagate it
everywhere**: abstract, contributions list, Theorem 7, and the conclusion.

If option (c) above is adopted, completeness can be strengthened to *relative
to sensor-signed metadata*, which is a materially stronger and defensible
claim. Note it as future work otherwise.

## R7-C3 — No update or deletion workflow

> BVCRSA is only designed for append-only industrial sensor streams, lacking
> standardized workflows for hierarchical index and bitmap maintenance when
> sensor data are updated or deleted. In practical smart manufacturing,
> expired and faulty readings often need to be invalidated.

**Type:** functionality gap. **Severity: major.**

The Discussion concedes BVCRSA is "designed primarily for append-dominant IIoT
workloads," but the objection is concrete: faulty readings must be
invalidatable, and no mechanism exists.

### Fix

Specify a deletion workflow explicitly:

1. Gateway clears `B_u[pos_i] ← 0` for all `u ∈ Path(u_{i,j})`
2. Increments `ν_{u,b}` for affected blocks → forces re-masking, which is what
   prevents a stale-mask replay
3. Marks the aggregation entry `A_i` tombstoned so it is excluded from future
   aggregates
4. Recomputes affected `σ_{u,b}^{bmp}`, `Root_u^{bmp}`, `σ_u^{idx}`, and
   `Root_{e_q}`

⚠️ Note the security subtlety: a user who cached the *old* mask for version
`ν−1` can still unmask the old block. Version binding prevents forging a new
block but does not retroactively hide a deleted record from someone who
already reconstructed the bitmap. State this.

⚠️ **Also quantify it** — R3-11 asks the related question about epoch
recommitment cost. One experiment measuring index-update cost vs. number of
changed blocks answers both. Not yet scaffolded; add as Exp 12 if pursued.

## R7-C4 — Only offline cryptographic latency was measured

> All performance evaluations in this manuscript only measure offline
> cryptographic computation latency, while critical end-to-end overhead
> metrics including network transmission delay, blockchain interaction cost,
> and energy consumption of resource-constrained IIoT sensors are entirely
> excluded from analysis. Although each experiment is repeated for 20
> independent runs, no error bars or statistical confidence intervals are
> attached to performance curves to quantify result variance, which weakens
> the persuasiveness of experimental conclusions.

**Type:** experimental omission. **Severity: blocking.**
Also R1-C4, R2-C2, R3-17, R5-2.

### Fix — four parts, three now implemented

| Missing metric | Where it is now measured |
|---|---|
| Network / communication cost | **Exp 8** — actual KB per protocol round |
| Blockchain interaction cost | **Exp 11** — gas, anchor latency, finality, ledger growth |
| Sensor energy consumption | **Exp 9** — ⚠️ needs a real inline power-meter reading; the energy column stays blank and flagged `watts_measured=False` until one is supplied |
| Error bars / CIs | Structural — `harness.Experiment.record()` **rejects** any row lacking runs, stdev, ci95, and the raw sample list; every figure draws 95 % CI bars |

⚠️ Raw *network transmission delay* (wire RTT) is still not measured — Exp 8
gives payload size, not latency. Either add an RTT measurement between AWS
nodes, or state clearly that communication is reported as volume and that
transmission time depends on deployment link characteristics.

## R7-C5 — Single-node blockchain is not a consortium

> The blockchain prototype is only validated on a single-node Clique PoA
> private testnet deployed on a standalone machine, with a fixed block
> interval adopted for all experiments. No multi-node consortium cluster is
> constructed, and no comparative measurements under multiple epoch submission
> frequencies are conducted. Quantitative curves of ledger expansion,
> transaction gas cost and cross-node synchronization latency under multi-node
> networks and variable epoch cycles are absent. As a result, the manuscript
> cannot evaluate storage bloat and synchronization overhead under real
> industrial multi-party consortium chain deployments.

**Type:** experimental scope. **Severity: blocking.** Also R4-2.

Worse than the reviewer knows: the benchmark harness set `use_ethereum=False`
explicitly, so **no** reported number includes any chain interaction at all.

### Fix — **Experiment 11**

`Benchmark/11_Blockchain_Cost/experiment.py` sweeps block interval
`{1, 2, 5, 15} s` against node count, measuring gas per anchor, anchor
latency, finality (one block confirmation — the paper's stated acceptance
rule), `ledger_mb_per_year`, and cross-node sync latency.

The script **exits non-zero and writes no CSV** if no node answers — inventing
multi-node figures for a reviewer who is already unconvinced by the
single-node setup would be indefensible. With one node connected,
`sync_latency_ms` is left blank and the row is annotated
`single-node: sync latency not measurable (R7-C5)`.

⚠️ **A single-node re-run does not answer this comment.** Stand up at least
3 nodes before claiming consortium applicability:

```bash
export BVCRSA_NODE_RPCS=http://10.0.1.10:8545,http://10.0.1.11:8545,http://10.0.1.12:8545
export BVCRSA_BLOCK_INTERVALS=1,2,5,15
```
