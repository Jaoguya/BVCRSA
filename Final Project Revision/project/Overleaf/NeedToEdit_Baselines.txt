6. [DECISION] Latt-IBEKS trapdoor sampling -- forgeable, needs disclosure
    Section: V, wherever Latt-IBEKS's trapdoor cost is cited
--------------------------------------------------------------------------------
The trapdoor sampler implemented for this baseline (MP12 gadget trapdoor,
deterministic preimage) is demonstrably forgeable -- ~204 observed
trapdoors let an attacker recover the master trapdoor R exactly and forge
trapdoors for unqueried keywords. A randomization fix was attempted this
session and confirmed NOT to work (the published trapdoor structurally
reveals both halves of the relevant equation regardless of randomization;
real Gaussian perturbation sampling is needed, which is high-risk to
implement correctly under time pressure -- deliberately not attempted).

Consequence: Latt-IBEKS's measured trapdoor-gen cost (~1ms) is a LOWER
BOUND, not ref28's real cost. Ref28's own Fig. 2(b) puts their trapdoor
at ~300s at n=17.

DECIDE ONE:
  (a) Implement real Gaussian sampling before submission (highest-risk
      code in the suite -- budget accordingly).
  (b) Report Latt-IBEKS's trapdoor cost as an explicit lower bound
      alongside ref28's real ~300s figure, and disclose the substitution.
      Exp 01 headline flips from "BVCRSA loses by ~3x" to "BVCRSA wins by
      ~10^5x" depending on which number is cited -- pick one and say why.

Full technical writeup: Benchmark/_shared/latt_ibeks.py module docstring.

7. [DECISION] Trinity's query cost is inflated by a benchmark-design
   mismatch, not representative of ref26's real cost
    Section: V, Query Processing Time / Query Throughput
--------------------------------------------------------------------------------
Forcing a 1-D numeric range query onto one axis of Trinity's 3-D Hilbert
curve, with the other two axes unconstrained, fragments the query into
thousands of Hilbert intervals (11,381 at N=1,000) and tens of thousands
of tokens (18,558), driving millions of HMAC operations per query. This
is a worst case for ref26's data structure, not a fair characterization
of it -- Trinity is designed for genuine spatio-temporal box queries.

DECIDE ONE:
  (a) Disclose the mapping and the resulting fragmentation as a stated
      limitation of this comparison (cheap, one paragraph).
  (b) Add a second sweep posing a real spatio-temporal query where
      Trinity is used as designed, alongside the current one.

Do not present current Trinity latency numbers as ref26's inherent cost
without one of the above.

8. [DECISION] BVCRSA's own ABSE.Test doesn't check PP/MSK (pre-existing,
   not introduced this session, but still open)
    Section: Security Analysis / wherever ABSE.Test cost is quoted
--------------------------------------------------------------------------------
test() performs a real pairing but the policy check is a plaintext `in`
test -- every measured ABSE.Test timing authorizes nobody. Fixing this
(concrete form of R1-C2/R3-4) will likely RAISE BVCRSA's own measured
cost. Budget for that before quoting any final Exp02 number as the
paper's headline. Needs a real concrete ABSE construction with an actual
policy-satisfaction check inside test(), not a pairing that always
succeeds regardless of the caller's attributes.

9. [DECISION] Index-pruning disclosure (F1)
    Section: V, Query Processing Time, wherever the comparison is
    introduced
--------------------------------------------------------------------------------
BVCRSA is the only scheme in the comparison permitted to prune candidates
via an index (context filter + bitmap) before any pairing runs -- 0.16
pairings/doc measured, vs. VC-KASE's 1.00 and ABSE-Range's 5.26. This is
legitimate (a linear scan is faithful to what VC-KASE/ABSE-Range/
Latt-IBEKS's papers actually specify), but a reader will otherwise assume
all five schemes scan the candidate set equally. State explicitly that
much of BVCRSA's Exp02 advantage is algorithmic pruning, not cheaper
per-operation cryptography.

10. [DECISION] Query-scope / selectivity mismatch (E1')
    Section: V, wherever schemes are first compared
--------------------------------------------------------------------------------
BVCRSA's trapdoor binds one (machine, t_slot) context; the baselines scan
all N for (sensor, range). Quantified at N=1,000: BVCRSA returns 6 of 11
true matches; Trinity, ABSE-Range, and Latt-IBEKS all return 11. BVCRSA is
partly faster because it searches a narrower query, not only because its
cryptography is cheaper.

DECIDE ONE:
  (a) Disclose the selectivity difference plainly (cheap).
  (b) Align all five schemes to one canonical query definition and
      re-run -- more defensible, more work, cost/benefit unclear given
      the AWS rerun already in flight.
